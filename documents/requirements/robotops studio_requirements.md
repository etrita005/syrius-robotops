# RobotOps Studio

## 1. 背景

现场 FAE 需要通过 Linux / Windows PC，经由 Wi‑Fi 连接机器人，对多台机器人进行统一查看、配置与升级。当前痛点通常包括：

- 设备分散，手工逐台连接成本高
- 不同机器人基础信息与版本状态需要快速核对
- BSP、机器人操作系统、应用地图、程序配置等升级/部署流程繁琐
- 多位 FAE 在不同现场重复配置，缺少可复用的“项目/解决方案”上下文

本工具目标是将“连接、识别、核对、升级、配置、记录”串成一个标准化流程，减少人工错误，提高现场操作效率。

---

## 2. 产品定位

本软件定位为 **现场机器人管理与升级工具**，面向 FAE 使用，不面向终端客户日常操作。

### 2.1 核心定位

- 面向现场多台机器人批量管理
- 支持 Wi‑Fi 网络连接
- 支持查看/修改机器人基础信息
- 支持 BSP 升级、机器人操作系统升级
- 支持应用地图与程序配置的部署/更新
- 支持可复用的 project/solution 机制，减少重复配置

### 2.2 推荐形态

**推荐优先做 GUI，而不是纯 TUI。**

原因：
- 现场要处理多台机器人、多个版本包、多个配置项，GUI 更容易呈现设备状态、风险提示和升级进度
- FAE 使用场景强调“看得见、点得清、出错少”，GUI 更适合做批量勾选、状态对比、任务队列、日志查看
- project/solution 文件的导入导出、设备列表管理、升级流程编排，GUI 更便于理解和审核

可选策略：
- **主产品：GUI**
- **辅助能力：命令行/TUI 或无头模式** 可作为后续扩展，用于自动化、批量脚本或低带宽场景

---

## 3. 目标用户与使用场景

### 3.1 用户角色

- **FAE（主要用户）**：在现场连接机器人、确认状态、升级与配置
- **高级 FAE / 技术支持**：需要分享 project/solution、复现问题、导出日志
- **管理员（可选）**：维护升级包、模板、默认配置、权限策略

### 3.2 典型场景

1. FAE 到达现场，打开软件，加载已有 project/solution
2. 软件自动发现局域网内机器人，或从预置列表连接
3. FAE 选择要管理的机器人，查看 SN、固件版本、软件版本、在线状态
4. FAE 执行 BSP 升级或机器人操作系统升级
5. FAE 同步应用地图和程序配置
6. 操作完成后导出日志与结果报告
7. 下次到同一现场，直接打开同一 project/solution 继续操作

---

## 4. 设计原则

- **少配置、可复用**：尽量把现场环境信息沉淀到 project/solution
- **可追踪、可回滚**：所有升级与配置操作需可记录、可审计、可回看
- **批量优先**：支持多台机器人列表视图与批量操作
- **安全优先**：升级和修改信息必须有明确确认、校验和失败处理
- **断点友好**：现场网络不稳定，操作流程应支持中断恢复和结果重试

- 别名（Alias）

机器人基础信息（动态获取，当前阶段由前端模拟）包括：
- Model

- ThingsId
- VendorId
- ProductId
- 主控板 SN
- 主控板 Id
- 主控 SOM Id

系统需要支持修改以下持久化字段：
- 别名（Alias）
- 机器人IP / mDNS地址（Address）

机器人其他信息包括：
- 硬件设备树
  - 硬件名字
  - 固件版本
  - 硬件版本
  - 硬件 SN
  - 硬件 Id

软件版本信息包括：
- megaCosmOS 版本（机器人操作系统）

硬件版本信息包括：
- 主控硬件版本

### 5.1.3 升级能力
- BSP 升级
- 机器人操作系统升级
- 升级包校验、选择、上传、执行、进度显示、结果记录
- 支持单台与多台机器人批量执行

#### 5.1.4 应用地图与程序配置
- 应用地图导入/下发/更新
- 程序配置导入/下发/更新
- 配置版本管理
- 配置一致性检查

#### 5.1.5 Project / Solution
- 新建 project/solution
- 保存 project/solution
- 打开 project/solution
- 导入/导出 project/solution 文件
- 分享给其他 FAE 使用后无需重新配置

#### 5.1.6 现场诊断模式（新增核心模块）

系统应提供独立的 Diagnostic / Health Check 模式，用于现场诊断、状态分析、故障排查与升级确认。

该模式应支持：

- 磁盘分区使用率
- CPU 实时利用率
- GPU 实时利用率
- 内存实时使用情况
- SWAP 使用情况
- I/O 实时情况

#### 实时告警与历史告警
- 实时告警事件列表
- 历史告警事件列表
- 告警等级显示
- 告警时间线
- 告警过滤与搜索

#### 系统运行状态
- 开机时长（Uptime）
- 当前系统时间
- 时间同步状态
- OTA 状态
- OTA 进度

#### 日志能力

- 日志上传状态与结果显示

示例：
- Camera → 视频流/图像
- LiDAR → 点云/扫描图
- IMU → 曲线图
- Battery → 仪表盘

#### 网络诊断
- 网络连通性测试
- Ping 测试
- 带宽测试
- 延迟测试
- Wi‑Fi 信号强度

#### 关键进程与服务监控
- systemd 服务状态
- 关键进程状态
- 关键进程 CPU 利用率
- 关键进程内存利用率
- 关键进程 I/O 情况
- 异常退出检测

#### 健康检查报告
- 自动生成 PASS / WARNING / FAIL 诊断结果
- 支持导出现场健康检查报告
- 支持升级前/升级后状态对比

### 5.1.7 日志与报告
- 记录每次连接、发现、升级、配置操作的结果
- 导出现场操作报告
- 导出错误日志与诊断信息

- 机器人业务运行监控大屏
- 远程控制机器人运动
- 多用户云协作同步
- 与云端设备管理平台深度打通
- 自动灰度升级调度

## 6. 关键需求：GUI 还是 TUI

### 6.1 结论

建议 **GUI 作为主形态**。

### 6.2 原因

- 设备状态、版本、升级进度、告警信息需要强可视化
- project/solution、配置模板、升级包之间存在关联，GUI 更利于组织
- FAE 现场操作往往要边看边比对，GUI 降低误操作概率
- 批量操作中，表格、筛选、勾选、状态颜色提示非常关键

### 6.3 TUI 的适用位置

TUI 不建议作为主产品，但可以保留以下价值：

- 作为后续自动化接口的桥梁
- 作为轻量应急模式
- 作为 headless/SSH 场景备用能力

### 6.4 建议策略

- 第一阶段：GUI-only
- 第二阶段：补充 CLI/TUI 或 API 层

## 7. 设备发现与连接

### 7.1 连接方式

软件应支持以下连接来源：

1. **主动发现**（可选）
   - 扫描局域网内机器人
   - 发现后自动识别设备信息
   - 发现结果可加入当前 project/solution

2. **预配置机器人列表**
   - 用户预先导入 IP / 主机名 / MAC / 序列号等信息
   - 适合现场已知设备集群
   - 建议作为默认主方式之一

3. **手动添加**
   - 手动录入单台机器人信息
   - 适合临时接入或异常排查

### 7.2 发现能力要求

- 支持开启/关闭主动发现
- 支持设置发现范围、网段、超时时间
- 支持发现结果去重与身份匹配
- 支持将发现到的设备与已有预配置条目合并

### 7.3 设备身份匹配优先级（建议）

建议采用以下匹配优先级：
1. SN
2. MAC
3. 固定设备 ID
4. IP 地址

IP 不应作为唯一身份，因为现场网络环境变化较大。

## 8. project / solution 机制

### 8.1 目标

project/solution 的目标是把现场环境、机器人清单、包版本、配置模板、常用连接方式和操作历史沉淀下来，做到：

- 下次打开软件可以直接恢复现场上下文
- 分享给其他 FAE 后可以快速接手
- 降低重复配置成本

### 8.2 概念建议

建议采用以下层次：

#### 8.2.1 Solution
- 定义一个现场或一个客户项目的总上下文
- 包含机器人列表、网络信息、模板、包引用、操作策略
- 可被导出/分享

#### 8.2.2 Project
- 如果需要比 solution 更细粒度，可用于一个具体交付任务或一次现场活动
- 也可以简化为只保留一个层级，避免用户概念负担

### 8.3 推荐做法

为了降低复杂度，建议先做 **单层 project/solution 概念**：

- 对用户界面统一称为 **Project** 或 **Workspace**
- 文件中保存：
  - 机器人列表
  - 发现/连接配置
  - 升级包引用路径
  - 地图/程序配置模板
  - 最近操作记录
  - 用户备注
  - 版本兼容信息

如果后续确实需要更复杂层次，再拆分成 solution + project。

### 8.4 文件要求

- 可导入/导出为单一文件或一个目录包
- 文件需具备版本号，方便以后扩展字段
- 文件内容需可校验兼容性
- 引用外部大文件时，应支持相对路径或资源包打包

### 8.5 复用要求

- 可在另一台 PC 上打开同一个 project/solution
- 若缺少资源文件，应提示缺失项并引导重新定位
- 同一 project/solution 可被多名 FAE 共享使用

## 9. 功能需求

### 9.1 设备管理

系统应支持：
- 新增、编辑、删除机器人条目
- 按名称、SN、IP、版本、状态过滤与排序
- 设备分组、标签、备注
- 在线/离线状态刷新
- 批量选择设备执行操作
- 管理机器人 Wi‑Fi 配置
- 查看设备硬件拓扑

### 9.2 基础信息查看/修改

系统应支持显示以下基础信息：
- Model（动态获取，只读）
- RobotSN（动态获取，只读）
- ThingsId（动态获取，只读）
- VendorId（动态获取，只读）
- ProductId（动态获取，只读）
- 主控板 SN（动态获取，只读）
- 主控板 Id（动态获取，只读）
- 主控 SOM Id（动态获取，只读）

系统应支持修改以下持久化字段：
- 别名（Alias）
- 机器人IP / mDNS地址（Address）

系统应支持显示软件版本信息（动态获取，只读）：
- megaCosmOS 版本
- Movebase 版本
- GGR 版本
- MCU 板卡固件版本
- 执行器固件版本
- 传感器固件版本

系统应支持显示硬件版本信息：
- 主控硬件版本
- MCU 板卡硬件版本
- 执行器硬件版本
- 传感器硬件版本

系统应支持显示机器人硬件设备树：
- 硬件名称
- 固件版本
- 硬件版本
- 硬件 SN
- 硬件 Id
- 父子节点关系
- 在线状态

系统应支持 Wi‑Fi 配置管理：
- 查看当前 Wi‑Fi 配置
- 修改 Wi‑Fi SSID
- 修改 Wi‑Fi 密码
- 支持 DHCP / Static IP 配置
- 支持保存多个 Wi‑Fi Profile
- 支持 Wi‑Fi 配置导入/导出
- 支持 Wi‑Fi 配置批量下发

### 9.3 BSP 升级

系统应支持：
- 选择 BSP 包
- 校验包完整性
- 查看包版本、适配机型、发布日期
- 对单台或多台机器人执行升级
- 显示升级步骤与进度
- 失败后支持重试或回退策略（若设备侧支持）
- 记录升级结果

### 9.4 机器人操作系统升级

系统应支持：
- 选择 OS 升级包
- 版本兼容性检查
- 升级前预检（电量/连接/空间/依赖项等，具体条件可配置）
- 升级执行与过程日志
- 完成后自动校验版本

### 9.5 应用地图与程序配置

系统应支持：
- 导入地图文件
- 导入程序配置文件
- 绑定目标机器人
- 下发/更新/覆盖/保留策略选择
- 校验配置版本一致性
- 配置发布前预览差异

### 9.6 批量任务

系统应支持批量任务队列：
- 选择多台设备
- 统一发起任务
- 按设备独立显示进度和结果
- 支持失败设备单独重试
- 支持任务暂停/取消（若底层协议支持）

### 9.7 日志、审计与导出

系统应支持：
- 操作日志
- 设备事件日志
- 错误日志
- 结果汇总报告导出（HTML / PDF / JSON / CSV 中至少一种，建议先支持 JSON + CSV）

## 10. 非功能需求

### 10.1 兼容性

- 支持 Windows PC
- 支持 Linux PC
- 支持 Wi‑Fi 网络环境

### 10.2 易用性

- 首次使用应能在 5 分钟内完成基本连接和 project 打开
- 常见操作路径不应要求用户多次重复输入相同信息
- 错误提示需包含可执行建议，而不只是错误码

### 10.3 可靠性

- 网络中断后不应导致 project 文件损坏
- 升级过程中的失败必须可追踪
- 操作过程中应避免因界面关闭导致未保存数据丢失

### 10.4 安全性

- project/solution 文件中不得明文保存不必要的敏感信息
- 升级包和配置包应支持签名或校验和验证（如适用）
- 对危险操作设置二次确认
- 支持操作权限分级（可选）

### 10.5 性能

- 设备发现应在可接受时间内返回结果
- 多台设备列表刷新不应明显卡顿
- 操作日志和结果查询应快速响应

## 11. 配置与数据管理

### 11.1 本地数据

建议本地保存：
- 最近打开的 project/solution
- 设备缓存
- 最近使用的升级包路径
- 用户界面偏好设置

### 11.2 外部资源

建议统一管理：
- BSP 包
- OS 包
- 地图文件
- 程序配置文件

### 11.3 版本管理

每个资源应记录：
- 文件名
- 版本号
- 来源
- 校验信息
- 适配范围

---

## 12. 错误处理原则

- 可恢复错误：提示用户重试并保留现场上下文
- 不可恢复错误：明确终止原因，并建议下一步动作
- 多设备批量任务中，单台失败不应阻断其他设备执行，除非是全局前置条件失败

---

## 13. 需要你确认的决策点

以下决策会影响后续 UI 交互稿：

1. **SN / 固件版本 / 软件版本是否允许修改？**
   - 还是只读展示？

2. **project 与 solution 是否需要区分两个概念？**
   - 当前建议统一为 Workspace / Project
   - 暂不拆分双层结构

3. **主动发现是否必须支持？**
   - 当前建议作为可选增强功能
   - 默认仍支持预配置机器人列表

4. **升级包是否由本软件管理本地文件，还是只引用外部路径？**

5. **是否需要权限/账号体系？**
   - 例如只读用户、FAE 用户、管理员

## 15. 待确认的假设

本草案默认假设：
- 机器人可通过网络 API 或协议被读取/配置
- 升级包、地图、程序配置均可由 PC 侧作为文件管理
- 现场网络环境可能不稳定，因此流程必须具备容错能力
- FAE 需要在多个现场之间复用同一套工作流
