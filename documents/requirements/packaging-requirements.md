# 应用打包与交付 — 需求规格说明书

## 1. 概述

应用打包与交付能力用于将 RobotOps Studio 构建为面向现场 FAE 的零环境依赖本地运行程序。系统最终以各平台独立单文件二进制程序交付，用户无需安装 Node.js、npm、Nginx、Electron、系统运行库或其他配套软件，即可在目标机器上直接启动后端内置 HTTP 服务，并通过本地浏览器访问 Web UI。

本需求覆盖前端静态构建、后端 HTTP 服务承载、前端资源内嵌、外置配置、跨平台打包、压缩与运行验收等内容。

**关键用例**：FAE 从发布包中获取与当前系统匹配的单个可执行文件，放置到任意本地目录，按需修改同目录 `config.json`，双击或命令行启动后，在浏览器访问 `http://127.0.0.1:<端口>` 完成机器人运维操作。

---

## 2. 术语定义

| 术语 | 定义 |
|------|------|
| **前端静态产物** | 前端通过 Vite 构建生成的纯静态 `dist` 内容，包括 HTML、CSS、JavaScript、字体、图片等资源。 |
| **内置 HTTP 服务** | 后端二进制程序启动的本地 HTTP 服务，同时提供业务 API 与前端静态资源访问能力。 |
| **单文件二进制程序** | 每个平台单独产出的一个可执行文件，内部包含 Node.js 运行时、后端代码与前端静态资源。 |
| **外置配置文件** | 与可执行文件位于同一目录的 `config.json`，用于保存端口、数据库、密钥等可变配置。 |
| **SPA 兜底路由** | 当前端路由路径无法匹配静态文件或 API 时，后端返回内嵌的 `index.html`，避免浏览器刷新后出现 404。 |
| **pkg 打包** | 使用 `pkg` 将 Node.js 后端打包为跨平台独立可执行文件的构建方式。 |
| **目标平台** | 需要交付二进制程序的操作系统与 CPU 架构组合，包括 Windows、macOS Intel、macOS Apple Silicon、Linux amd64、Linux arm64。 |

---

## 3. 设计原则

1. **零环境依赖**：目标机器不要求预装 Node.js、npm、Nginx、Electron、运行库或其他依赖软件。
2. **单进程承载**：一个后端进程同时承载业务 API 与前端静态资源，不引入额外 Web Server。
3. **浏览器交互**：不开发 Electron 桌面客户端，用户自行打开本地浏览器访问服务。
4. **静态资源内嵌**：Vite 构建后的前端 `dist` 必须内嵌进后端二进制，不单独分发静态目录。
5. **配置外置可改**：端口、数据库、密钥等部署现场可变配置放在同目录 `config.json`，修改配置不需要重新打包。
6. **平台产物独立**：不同平台使用独立单文件二进制程序，不要求用户下载源码、依赖目录或构建工具。
7. **一键全平台构建**：开发者在 Windows、macOS、Linux 任一系统上均可通过一个命令生成所有目标平台产物。
8. **体积可控**：构建流程应支持压缩，降低最终二进制体积。
9. **刷新友好**：内置 SPA 兜底路由，前端任意路由页面刷新后不应出现静态资源 404。

---

## 4. 非目标

以下能力明确不在本需求范围内：

- 不开发 Electron、Tauri 或其他桌面壳客户端。
- 不要求目标机器安装或运行 Nginx、Apache、Caddy 等外部静态资源服务器。
- 不交付源码包、`node_modules`、前端 `dist` 目录或后端构建目录作为运行必需内容。
- 不覆盖移动端、Web 云部署、容器镜像部署或 Kubernetes 部署形态。
- 不要求程序启动后自动打开浏览器。
- 不在本需求中定义业务 API 的具体字段与业务行为。
- 不支持 YAML 配置文件；配置文件格式固定为 JSON。

## 5. 目标平台与产物规范

### 5.1 支持平台（FR-PKG-001）

系统应支持同时生成以下目标平台的可执行文件：

| 平台 | 架构 | 产物示例 |
|------|------|----------|
| Windows | amd64 | `robotops-studio-windows-amd64.exe` |
| macOS | amd64（Intel） | `robotops-studio-macos-amd64` |
| macOS | arm64（Apple Silicon / M 系列） | `robotops-studio-macos-arm64` |
| Linux | amd64 | `robotops-studio-linux-amd64` |
| Linux | arm64 | `robotops-studio-linux-arm64` |

### 5.2 单文件交付（FR-PKG-002）

每个目标平台应产出独立单文件二进制程序。

运行必需内容仅包括：

1. 对应平台的单文件二进制程序。
2. 可选的同目录 `config.json` 外置配置文件。

不得要求用户同时携带以下内容：

- 项目源码目录。
- `node_modules` 目录。
- 前端 `dist` 静态目录。
- 后端编译输出目录。
- npm、pnpm、yarn 或其他包管理器。
- Nginx 或其他外部 Web Server 配置。

### 5.3 产物目录（FR-PKG-003）

全平台构建完成后，构建输出目录应按平台清晰组织，例如：

```text
release/
├── windows-amd64/
│   ├── robotops-studio.exe
│   └── config.example.json
├── macos-amd64/
│   ├── robotops-studio
│   └── config.example.json
├── macos-arm64/
│   ├── robotops-studio
│   └── config.example.json
├── linux-amd64/
│   ├── robotops-studio
│   └── config.example.json
└── linux-arm64/
    ├── robotops-studio
    └── config.example.json
```

`config.example.json` 为示例配置文件，不应包含真实密钥、密码、Token 或生产环境敏感信息。

## 6. 构建流程需求

### 6.1 前端 Vite 静态构建（FR-PKG-004）

系统应先执行前端 Vite 构建，生成纯静态前端资源。

构建要求：

- 前端构建输出目录为 `dist` 或构建脚本明确指定的等价目录。
- 产物必须可由普通静态文件服务器直接托管。
- 前端不得依赖 Vite 开发服务器运行时。
- 前端接口请求应使用相对路径或同源路径，以适配本地内置 HTTP 服务。
- 构建失败时应中断整体打包流程，并输出明确错误信息。

### 6.2 前端资源内嵌（FR-PKG-005）

系统应将前端 `dist` 内容内嵌进后端二进制程序。

内嵌要求：

- 打包后运行时不需要读取外部 `dist` 目录。
- 二进制程序内部应包含 `index.html`、静态脚本、样式、图片、字体等前端资源。
- 内嵌资源应保留文件路径关系与 MIME 类型识别能力。
- 若内嵌资源缺失或损坏，程序启动或访问首页时应给出可诊断的错误日志。

### 6.3 后端 pkg 打包（FR-PKG-006）

系统应使用 `pkg` 将 Node.js 后端打包为各平台单文件二进制程序。

打包要求：

- 后端源码应先完成 TypeScript 编译或由构建流程转换为 `pkg` 可处理的 JavaScript 入口。
- `pkg` 配置应包含后端运行必需代码与内嵌前端静态资源。
- 打包过程不得依赖全局安装的 `pkg`，应使用项目本地依赖或包管理器脚本调用。
- 构建脚本应支持一次性生成全部目标平台产物。
- 构建命令应可在 Windows、macOS、Linux 任一开发机执行，并生成全部目标平台产物。

### 6.4 一键全平台打包命令（FR-PKG-007）

项目应在 `src/package.json` 提供一个产品级统一命令完成全平台打包。`src/package.json` 作为前后端构建编排入口，协调 `src/frontend` 与 `src/backend` 两个子包完成构建、资源整合、pkg 打包、压缩与 release 校验。

该命令至少应顺序执行：

1. 安装依赖检查或依赖完整性检查。
2. 前端 Vite 静态构建，输出到 `src/frontend/dist`。
3. 前端 `dist` 资源内嵌准备，复制或转换到后端打包上下文。
4. 后端 TypeScript 构建。
5. `pkg` 全目标平台打包。
6. 二进制压缩。
7. 产物复制与目录整理。
8. 基础启动校验或产物存在性校验。

统一命令为：

```bash
npm --prefix src run package:all
```

在 `src/` 目录下也可执行：

```bash
npm run package:all
```

### 6.5 压缩能力（FR-PKG-008）

构建流程应支持压缩最终二进制程序，以降低交付体积。

压缩要求：

- 压缩步骤应作为标准全平台构建流程的一部分，或提供明确开关。
- 压缩失败不应静默忽略，应在构建日志中明确提示。
- 压缩后的程序应保持可执行、可启动、可访问前端与业务 API。
- 若某平台压缩工具不可用，构建流程应给出明确说明，并允许按配置决定失败或跳过。

## 7. 运行时服务需求

### 7.1 内置 HTTP 服务（FR-PKG-009）

二进制程序启动后应在本机启动内置 HTTP 服务。

服务职责包括：

- 提供 RobotOps Studio 后端业务 API。
- 托管内嵌前端静态资源。
- 提供 SPA 兜底路由。
- 输出启动地址与端口等必要运行信息。

默认监听地址为 `127.0.0.1`，默认端口由 `config.json` 或内置默认值提供。

### 7.2 浏览器访问方式（FR-PKG-010）

用户通过本地浏览器访问：

```text
http://127.0.0.1:<端口>
```

系统不要求自动打开浏览器。启动日志或终端输出应明确提示访问地址。

### 7.3 API 与静态资源路由分离（FR-PKG-011）

后端应区分业务 API 路由与前端静态资源路由。

推荐规则：

- `/api/**`：业务 API。
- `/assets/**` 或 Vite 构建生成的静态路径：前端静态资源。
- 其他非 API GET 请求：按 SPA 兜底路由处理。

当 `/api/**` 不存在时，应返回 API 错误响应，不应返回 `index.html`。

### 7.4 SPA 兜底路由（FR-PKG-012）

系统应内置 SPA 兜底路由，解决前端页面刷新 404 问题。

行为要求：

- 访问 `/` 返回内嵌 `index.html`。
- 访问前端路由路径（如 `/solutions/123`、`/artifacts`）时返回内嵌 `index.html`。
- 访问真实存在的静态资源时返回对应资源。
- 访问不存在的静态资源文件时应返回 404，不应错误返回 `index.html`。
- 非 GET / HEAD 请求不得触发 SPA 兜底。

### 7.5 端口冲突处理（FR-PKG-013）

默认采用固定端口策略。

- 程序从 `config.json` 读取端口；若未配置，则使用内置默认端口。
- 若端口被占用，程序启动失败。
- 启动失败时应输出明确错误，提示用户修改同目录 `config.json` 中的端口后重启。
- 程序不得在端口冲突时自动递增或随机选择其他端口。

## 8. 外置配置需求

### 8.1 配置文件格式（FR-PKG-014）

系统应支持同目录 JSON 配置文件：

```text
config.json
```

不支持 YAML 配置文件。

### 8.2 配置查找规则（FR-PKG-015）

程序启动时应优先读取与当前可执行文件同目录的 `config.json`。

读取规则：

1. 若 `config.json` 存在，读取并解析配置。
2. 若 `config.json` 不存在，使用内置默认配置启动。
3. 若 `config.json` 存在但 JSON 格式非法，程序启动失败并提示配置文件路径与解析错误。
4. 若配置字段类型非法，程序启动失败并提示具体字段。

### 8.3 配置内容（FR-PKG-016）

`config.json` 应至少支持以下配置项：

```json
{
  "server": {
    "host": "127.0.0.1",
    "port": 3000
  },
  "database": {
    "path": "./data/robotops.db"
  },
  "security": {
    "secret": "change-me"
  },
  "logs": {
    "level": "info",
    "dir": "./logs"
  }
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `server.host` | string | 否 | HTTP 监听地址，默认 `127.0.0.1`。 |
| `server.port` | number | 否 | HTTP 监听端口，未配置时使用内置默认端口。 |
| `database.path` | string | 否 | 本地数据库文件路径或数据目录路径。 |
| `security.secret` | string | 否 | 本地密钥类配置，不应写入示例真实值。 |
| `logs.level` | string | 否 | 后端日志等级。 |
| `logs.dir` | string | 否 | 日志输出目录。 |

具体配置字段可随后端实际模块扩展，但应保持向后兼容。

### 8.4 配置安全（FR-PKG-017）

- 示例配置不得包含真实密钥、密码、Token 或生产凭据。
- 日志不得输出 `security.secret` 等敏感字段明文。
- 配置解析错误可以输出字段路径与错误原因，但不得输出敏感字段值。

## 9. 非功能需求

### 9.1 兼容性（NFR-PKG-001）

产物应在目标平台常见版本上运行，包括：

- Windows 10 及以上。
- macOS Intel 机型。
- macOS Apple Silicon 机型。
- 主流 Linux amd64 发行版。
- 主流 Linux arm64 发行版。

### 9.2 可用性（NFR-PKG-002）

用户启动程序后，应能通过日志或终端输出快速确认：

- 程序已启动成功。
- 当前监听地址与端口。
- 配置文件是否加载成功。
- 前端访问 URL。

### 9.3 可诊断性（NFR-PKG-003）

以下异常应有明确错误信息：

- 配置文件不存在且使用默认配置。
- 配置文件 JSON 解析失败。
- 配置字段校验失败。
- 端口被占用。
- 内嵌前端资源缺失。
- 业务 API 初始化失败。
- 打包流程中前端构建、后端构建、pkg 打包或压缩失败。

### 9.4 安全性（NFR-PKG-004）

- 默认监听地址应为 `127.0.0.1`，避免无意暴露到局域网。
- 若允许配置为 `0.0.0.0`，应在日志中提示服务会暴露给网络内其他设备。
- 不得在启动日志、错误日志或构建日志中输出明文密钥、Token、密码。
- 静态资源托管不得允许目录穿越访问。

### 9.5 性能（NFR-PKG-005）

- 内嵌静态资源访问应支持合理缓存头，避免重复加载大型前端资源。
- 首页加载、静态资源读取与 API 响应不应因资源内嵌方式产生明显阻塞。
- 压缩后的二进制启动时间应满足现场工具使用需求，不应因极端压缩策略导致不可接受的启动延迟。

## 10. 验收标准

### 10.1 构建验收（AC-PKG-001）

执行全平台打包命令后，应满足：

- 前端 Vite 构建成功。
- 后端 TypeScript 构建成功。
- `pkg` 打包成功。
- 生成 Windows amd64、macOS amd64、macOS arm64、Linux amd64、Linux arm64 五类产物。
- 每个平台目录中存在单文件可执行程序。
- 前端 `dist` 目录不是运行必需交付内容。
- 构建日志中没有静默失败的压缩步骤。

### 10.2 运行验收（AC-PKG-002）

在目标平台启动对应二进制后，应满足：

- 无需安装 Node.js、npm、Nginx 或其他运行环境。
- 程序成功监听 `127.0.0.1:<端口>`。
- 浏览器访问 `/` 能打开前端首页。
- 浏览器访问前端子路由并刷新，页面不出现 404。
- 业务 API 路由可正常响应。
- `/api/**` 不存在路径返回 API 错误，而不是返回前端 HTML。

### 10.3 配置验收（AC-PKG-003）

配置文件行为应满足：

- 同目录 `config.json` 不存在时，程序使用默认配置启动。
- 修改 `config.json` 中端口后重启，程序监听新端口。
- 端口被占用时程序启动失败，并提示用户修改配置。
- 非法 JSON 配置导致程序启动失败，并输出可定位错误。
- 配置中的密钥字段不在日志中明文输出。

### 10.4 单文件验收（AC-PKG-004）

将单个平台可执行文件复制到一个空目录后，应满足：

- 在无源码、无 `node_modules`、无 `dist` 的情况下可以启动。
- 首页和静态资源可以正常访问。
- 若需要修改端口，只需新增或修改同目录 `config.json`。

## 11. 约束与风险

### 11.1 技术约束

- 后端必须使用 TypeScript 与 ES6 module 语法开发。
- 打包工具采用 `pkg`。
- 前端构建工具采用 Vite。
- 依赖必须通过项目本地包管理器安装，不得要求全局安装构建工具。
- 构建脚本不得依赖系统级包安装步骤。

### 11.2 风险项

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| `pkg` 对部分动态导入或原生依赖支持有限 | 打包后运行时报模块缺失 | 明确 `pkg` assets/scripts 配置，避免不可分析的动态路径，构建后执行启动校验。 |
| 前端资源内嵌路径处理不当 | 静态资源 404 或 MIME 类型错误 | 建立静态资源清单，运行时按路径与扩展名映射响应。 |
| 跨平台压缩工具差异 | 某些平台压缩失败 | 将压缩步骤参数化，失败时明确报告并保留未压缩产物策略。 |
| 任意本机全平台交叉构建 | 开发机环境差异导致构建不稳定 | 固化 npm 脚本、锁定依赖版本，在 CI 与三类本机系统上验证。 |
| 配置文件含敏感信息 | 日志泄露或误提交 | 提供 `config.example.json`，真实 `config.json` 加入忽略策略，日志脱敏。 |

以下事项不影响本需求方向，但需在实现设计或构建脚本落地时明确：

1. 内置默认端口为 `30001`。
2. 最终全平台打包命令为 `npm --prefix src run package:all`。
3. 当前 `pkg` 使用 Node 18 目标版本，后续升级需验证 base binary 可用性。
4. 二进制压缩工具与失败策略。
5. 前端内嵌资源清单生成方式。
6. `config.json` 完整 Schema 与字段校验规则。
